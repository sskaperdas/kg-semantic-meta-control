# Πτυχιακή: Evidence-Gated Semantic Meta-Control για Knowledge Graph Link Prediction

## 0. Τι είναι αυτή η εργασία

Έχουμε ήδη ή θα έχουμε ένα embedding-based μοντέλο για Knowledge Graph Completion / Link Prediction.  
Το μοντέλο παίρνει ένα ερώτημα τύπου:

```text
(h, r, ?)
```

και επιστρέφει μία λίστα από υποψήφιες απαντήσεις με scores.

Το πρόβλημα είναι ότι το μοντέλο ταξινομεί με βάση αριθμητικό score, όχι με βάση semantic reasoning.  
Άρα μπορεί να βάλει πολύ ψηλά μία απάντηση που είναι λογικά/σημασιολογικά λάθος.

Η δική σου δουλειά είναι να φτιάξεις ένα **post-hoc semantic control layer** που δουλεύει **μετά** το μοντέλο:

```text
trained model -> candidate predictions -> semantic checking -> re-ranking -> abstention -> final output
```

Δεν αλλάζεις το μοντέλο.  
Δεν κάνεις retraining μέσα στη δική σου υλοποίηση.  
Δεν φτιάχνεις νέο neural model.

Φτιάχνεις έναν ελεγκτή που αποφασίζει αν οι προβλέψεις του μοντέλου είναι σημασιολογικά αποδεκτές.

## 2. Τι σημαίνουν τα semantic sidecars

Τα semantic sidecars είναι τα αρχεία που θα χρησιμοποιήσεις για να ελέγξεις αν ένα candidate είναι σημασιολογικά σωστό.

### 2.1 `entity_types.json`

Λέει τι type έχει κάθε entity.

Παράδειγμα από DrugBank:

```json
{
  "drug:DB00001": ["Drug"],
  "target:BE0000048": ["Target"],
  "enzyme:BE0001234": ["Enzyme"]
}
```

Παράδειγμα από EurostatKG:

```json
{
  "https://.../some_entity": [
    "https://.../GlossaryArticle",
    "https://.../Content"
  ]
}
```

### 2.2 `relation_constraints.json`

Λέει τι domain/range περιμένει κάθε relation.

Παράδειγμα από DrugBank:

```json
{
  "has_target": {
    "domain": ["Drug"],
    "range": ["Target"]
  }
}
```

Αυτό σημαίνει:

```text
(drug, has_target, target) -> valid
(drug, has_target, category) -> invalid
(drug, has_target, pathway) -> invalid
```

Παράδειγμα από EurostatKG:

```json
{
  "https://ec.europa.eu/eurostat/NLP4StatRef/ontology/hasCode": {
    "domain": ["https://.../StatisticalData"],
    "range": ["https://.../Code"],
    "domain_short": ["StatisticalData"],
    "range_short": ["Code"]
  }
}
```

### 2.3 `class_hierarchy.json`

Χρησιμοποιείται για subclass reasoning.

Αν ένα entity έχει type:

```text
GlossaryArticle
```

και το `GlossaryArticle` είναι subclass του `Content`, τότε το entity μπορεί να θεωρηθεί και `Content`.

Αυτό είναι σημαντικό για semantic compatibility.

### 2.4 `disjoint_pairs.json`

Χρησιμοποιείται για incompatible classes.

Στο DrugBank υπάρχουν disjoint pairs μεταξύ βασικών entity classes, π.χ.:

```text
Drug != Target
Drug != Enzyme
Target != Category
```

Αυτό βοηθά στο να απορρίπτονται candidates με λάθος type.

## 3. Πού ξεκινάει η δική σου υλοποίηση

Η δική σου υλοποίηση ξεκινά από το να φτιάξεις έναν **semantic checker**.

Πριν καν έχεις τα τελικά model predictions, μπορείς να ξεκινήσεις με τα processed triples και τα semantic sidecars.

Ο πρώτος στόχος είναι να γράψεις κώδικα που να απαντά:

```text
Είναι το triple (h, r, t) σημασιολογικά αποδεκτό;
```

Παράδειγμα:

```text
(drug:DB00001, has_target, target:BE0000048) -> valid
(drug:DB00001, has_target, category:proteins) -> invalid
```

## 6. Βήμα 2 — Φτιάξε semantic checker

### Στόχος

Να φτιάξεις function που να κάνει:

```python
check_triple(h, r, t) -> result
```

όπου το `result` περιέχει:

```json
{
  "valid": true,
  "domain_ok": true,
  "range_ok": true,
  "reason": "domain and range compatible"
}
```

ή:

```json
{
  "valid": false,
  "domain_ok": true,
  "range_ok": false,
  "reason": "tail type Category is incompatible with expected range Target"
}
```

### Λογική για tail prediction

Για ένα query:

```text
(h, r, ?)
```

και candidate:

```text
t_candidate
```

ελέγχεις το triple:

```text
(h, r, t_candidate)
```

### Τι ελέγχεις

1. Πάρε types του head `h`.
2. Πάρε types του tail candidate `t`.
3. Πάρε domain/range της relation `r`.
4. Έλεγξε αν το head έχει συμβατό type με το domain.
5. Έλεγξε αν το tail έχει συμβατό type με το range.
6. Αν υπάρχει disjointness conflict, σημείωσέ το.

### Παράδειγμα DrugBank

```text
h = drug:DB00001
r = has_target
t = target:BE0000048
```

Expected:

```text
domain = Drug
range = Target
```

Result:

```json
{
  "valid": true,
  "domain_ok": true,
  "range_ok": true,
  "reason": "head type Drug matches domain; tail type Target matches range"
}
```

Invalid example:

```text
h = drug:DB00001
r = has_target
t = category:proteins
```

Result:

```json
{
  "valid": false,
  "domain_ok": true,
  "range_ok": false,
  "reason": "expected tail type Target, got Category"
}
```

## 8. Βήμα 4 — Candidate predictions από μοντέλο

Μετά το baseline training και το export candidates, θα πάρεις αρχεία τύπου:

```text
outputs/drugbank_core_<model>_tail_top50.jsonl
outputs/eurostatkg_structural_<model>_tail_top50.jsonl
```

Κάθε γραμμή είναι ένα query:

```json
{
  "query_type": "tail_prediction",
  "query": {
    "head": "drug:DB00001",
    "relation": "has_target",
    "gold_tail": "target:BE0000048"
  },
  "candidates": [
    {
      "entity": "target:BE0000048",
      "score": 12.3,
      "rank": 1,
      "is_gold": true
    },
    {
      "entity": "category:proteins",
      "score": 11.7,
      "rank": 2,
      "is_gold": false
    }
  ]
}
```

Παράδειγμα

Αν στο test set υπάρχει το triple:

drug:DB0001 has_target target:P12345

τότε για evaluation το query γίνεται:

(drug:DB0001, has_target, ?)

και το μοντέλο βγάζει candidates:

[
{ "entity": "target:P99999", "rank": 1, "is_gold": false },
{ "entity": "category:proteins", "rank": 2, "is_gold": false },
{ "entity": "target:P12345", "rank": 3, "is_gold": true }
]

Το target:P12345 είναι is_gold: true επειδή είναι το tail που υπήρχε στο αρχικό test triple.

Το μοντέλο έχει δώσει score.  
Εσύ θα προσθέσεις semantic information.

## 10. Βήμα 6 — Re-ranking

Αφού κάθε candidate έχει `semantic.valid`, κάνεις re-ranking.

### Πρώτη απλή πολιτική

```text
αν valid: κράτα το score
αν invalid: ρίξε το score πολύ χαμηλά
```

Παράδειγμα:

```text
reranked_score = score              αν valid
reranked_score = score - 1000       αν invalid
```

### Output

Προσθέτεις:

```json
{
  "reranked_score": -988.3,
  "new_rank": 50
}
```

Και ξαναταξινομείς τα candidates με βάση `reranked_score`.

---

## 11. Βήμα 7 — Abstention

Μετά το re-ranking, το σύστημα αποφασίζει αν θα απαντήσει.

### Πρώτη πολιτική

```text
αν δεν υπάρχει valid candidate στο top-K -> ABSTAIN
αλλιώς predict τον πρώτο valid candidate μετά το reranking
```

### Output query-level decision

```json
{
  "decision": "predict",
  "selected_entity": "target:BE0000048",
  "selected_score": 12.3
}
```

ή:

```json
{
  "decision": "abstain",
  "reason": "no semantically valid candidate in top-K"
}
```

### Τι είναι σημαντικό να δούμε

Το ιδανικό αποτέλεσμα είναι:

```text
semantic violations down
valid@K up
coverage reasonably high
ranking utility not destroyed
```

## 13. Τι να μην κάνεις

Μην αλλάξεις το embedding model.

Μην κάνεις retraining για να “διορθώσεις” τα semantic errors.

Μην βάλεις deep learning στο semantic layer.

Μην χρησιμοποιήσεις το gold answer για να αποφασίσεις αν ένα candidate είναι valid. Το `is_gold` είναι μόνο για evaluation.

Μην υποθέσεις ότι το μεγαλύτερο score σημαίνει semantic correctness.

---

## 14. Πώς να σκέφτεσαι την εργασία

Το embedding model απαντά:

```text
τι μοιάζει πιθανό;
```

Το semantic control layer απαντά:

```text
τι είναι αποδεκτό;
```

Η εργασία δεν προσπαθεί απλώς να αυξήσει Hits@10.  
Προσπαθεί να μειώσει semantic failures και να κάνει τις προβλέψεις πιο αξιόπιστες.

Ο τελικός στόχος είναι να μετατρέψουμε:

```text
score-only link prediction
```

σε:

```text
semantically controlled and explainable link prediction
```
